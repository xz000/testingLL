# 联机抖动方案深度对比：D 帧 vs 其它（2026-09-13）

> 背景/实测见 `FRAME_SYNC_ANALYSIS.md` 第五、六节。本文只做方案权衡。
> 实测要点（约 3000 帧，host/client 各一份）：**ping 6~8ms；client pending_max=1；sim ~52.5Hz（47~56）；
> host `[jit]` 182 次中 131 次（72%）紧邻 `waiting for client input`；时长为 33ms×125 / 50ms×43 / 67ms+×8 / 100ms+×6。**

---

## 0. 先厘清：问题分两层，方案各治哪层

| 层 | 症状 | 根因 |
|---|---|---|
| **A. sim 节拍** | sim 只有 ~52Hz（比 60 慢 13%）、帧间隔 33/50/100ms 抖 | host **必须等到新输入才产帧**（`try_emit` 的“等齐”），节拍被两端 update/输入到达牵着走 |
| **B. 画面观感** | 即使节拍有抖，看起来“一卡一卡” | 渲染直接取当前 sim 状态，**无插值**，抖多少就跳多少 |

**关键**：只做 B（插值）→ 画面顺了，但 sim 仍 52Hz → **整局慢放 13%**（移动/冷却/节奏都偏慢），这是功能性偏差。
只做 A → 节拍回到 60、抖动大减，但残余本机卡顿（67/100ms）仍会“顿一下”。
→ 两者互补；而 A 有两种实现：**D 帧延迟** 与 **held-continuous（保持连续量）**。

---

## 1. 三种候选机制

### 1.1 D 帧输入延迟（tagged input + buffer）
- client 把输入打**帧号** `N+D` 后发送；host **每 tick 定时产帧**，第 N 帧取 `tag==N` 的输入，缺则默认。
- 与现状的本质差别：host **不再等**；用“提前 D 帧产生”的输入保证到点即有。
- 延迟：所有输入统一 **+D·16.7ms**（D=1→17ms，D=2→33ms）。
- 需**协议改动**（输入包加 seq；`PROTOCOL_VERSION` +1）。

### 1.2 held-continuous（保持连续量、固定节拍）——推荐
- host **每 tick 定时产帧**；某端本 tick 没有“新输入”时，取该端**上一条输入**，但**只保留连续量**（`set_target`、以及持续中的移动），
  **丢弃离散动作**（`cast`/`queued`/`clear_queue`/`stop_move`）→ 避免重复施法。
- 真实输入到达后，其离散动作在**到达的那一帧**正常生效（最多晚 1 帧）。
- 延迟：连续量 **≈0 新增**（有就用新的，没有才用旧的）；离散量 ≤1 帧。
- **不需协议改动**：host 已有每端最近输入的字节，额外存一份 `last_input[client]` 即可；组帧仍在 host（权威）。

### 1.3 渲染插值（render interpolation）
- sim 照旧；绘制时按 `alpha = accumulator/TICK` 在 `prev → cur` 变换间 lerp（玩家/弹体/投射物）。
- 延迟：**输入 0 新增**；画面最多滞后 <1 个 sim 帧。
- 不改网络/协议/世界；但**不改变 sim 频率**。

## 2. 逐项对比

| 维度 | D 帧；输入延迟 | held-continuous | 渲染插值 |
|---|---|---|---|
| 新增输入延迟 | **+D 帧（全员、全部输入）** | 连续 ~0；离散 ≤1 帧 | **0** |
| sim 频率 | 回到 ~60（host 定时产帧） | 回到 ~60 | **不变（仍 ~52）** |
| 消除“等输入停摆” | ✅（靠提前 D） | ✅（靠 hold） | ❌ |
| 33ms（69%）| ✅ D≥1 | ✅ | 画面遮住，但当帧仍慢 |
| 50ms（24%）| D≥2 | ✅（靠 hold + 下帧补） | 画面遮住 |
| 67/100ms 本机卡顿（8%）| ❌（除非同时放大 host 追赶上限） | ❌（同上） | ✅ **视觉上抹平** |
| 整局慢放 13%（52Hz）| ✅ 修 | ✅ 修 | ❌ **不修** |
| 协议改动 | **需要**（seq + bump 版本） | 不需要 | 不需要 |
| 代码风险 | 高（netcode：缓冲/驱逐/迁移/重连/测试） | 中（host 组帧逻辑 + 单测） | 低（纯渲染） |
| 确定性 | 不变（host 权威） | 不变 | 不变 |
| 副作用 | 固定手感延迟；丢帧用默认可能丢一次操作 | 丢帧时离散动作晚 1 帧（连续不迟滞） | 渲染层多存一份上一帧状态 |
| 实现量 | 大 | 中 | 中 |

---

## 3. 为什么 held-continuous 在“手感延迟”上不输 D，甚至更好

- 我们的输入本来就是**电平量**：`set_target` 每帧重发（客户端已在做），`pending_cast` 也是持续到被接受。
- 所以“缺一帧输入”**不需要**用“提前 D 帧”的输入来救；直接用**上一条**即可，而且**不必给全局加 D 帧延迟**。
- D 会给**每一个输入**都加上 D 帧；held 只在该帧恰好缺输入时用上一条，且**只对离散动作**产生 ≤1 帧延迟。
- 结论：**held ≈ D=1 的稳定性，但延迟更低、且零协议改动。**

> 唯一理论差异：D 能让 host 精确知道“这条是给第 N 帧的”，而 held 是“最新可用”。对我们的电平输入模型，两者等价；
> 只有当一帧内到达多条输入、需要精确对齐时才需要 seq——而我们做的是“latest + hold”，不需要。

## 4. 对实测数据的效果预估

| 方案 | 预期 |
|---|---|
| 仅渲染插值 | 画面“一卡一卡”基本消失（33/50/67/100ms 都被插值覆盖），**但整局仍慢放 ~13%**、操作节奏偏慢 |
| 仅 held（固定节拍） | sim 回 ~60，**72% 与输入相关的抖动消除**；残余 67/100ms 本机卡顿仍会“顿”一下（无插值） |
| **held + 插值** | sim ~60 + 画面平滑；**覆盖全部三类症状**，不增输入延迟、不改协议 |
| D=1 | 类似 held（69%），但**全员 +17ms** 且需协议 |
| D=2 | 92% 抖动消除，但**全员 +33ms** 且需协议 |

---

## 5. 两个必须一起处理的细节

1. **host 追赶上限**：`MAX_CATCHUP_STEPS=4`（66ms）会把 >66ms 的本机卡顿“丢掉一部分时间”，这正是慢放的另一来源之一。
   固定节拍后，若某次 update 用了 100ms，最多只能补 4 帧（66ms）→ 仍丢 ~34ms。要么把上限调到 ~8，要么配合插值接受。
   （上限越大，突发越猛；插值可缓解观感。）
2. **坏帧/掉线**：`auto_drop_idle` 之后仍走 `default_input`；held 只在“未掉线但本 tick 无新输入”时生效。

---

## 6. 建议

**首选：held-continuous 固定节拍 + 渲染插值**（都不改协议）。
- 先把 host 改成“每 tick 定时产帧、缺输入 hold 连续量、丢离散”，恢复 60Hz；
- 再加渲染插值抹平残余本机卡顿；
- 用 `[stat]` 复测：目标 `sim≈60Hz`、`emit` 分桶 33ms 占比大幅下降、观感顺。

**备选：D=2 + 输入 seq**：如果 held 在实践中出现“离散动作丢失导致手感怪”，再退回 D（代价是协议 + 全员 33ms）。

**不建议单独做渲染插值**：画面顺了但整局 13% 慢放仍在（是功能性偏差，不只是观感）。
