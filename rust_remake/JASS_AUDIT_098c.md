### `A005`「Avatar hp」—— 深挖结论（2026-09-12，已复核）

#### 0. 归属：**化身模式（3）专属，与国王模式无关**（2026-09-12 复核）
`A005` 在整份 JASS 中只有 3 处使用，**全部在化身流程**：

| 位置 | 函数 | 作用 |
|---|---|---|
| `SetUnitAbilityLevel(Vn[FV],'A005', qn+12)` | `Bf`（回合布置） | 选定**新化身** `FV`，施加等级 `n+12` |
| `SetUnitAbilityLevel(Vn[gV],'A005', GV)` | `fI`（换人） | **还原旧化身** `gV`（同时逐项还原 `In`/`Hn`/`jn`/`Gn`、`S020→S001`、缩放回 .92） |
| `UnitAddAbility/RemoveAbility(Vn[0],'A005')` | 初始化 | 无 `SetUnitAbilityLevel`（等级 1 = 0），清理用 |

而**国王模式（4）**（`nn==4`，`kV`/`KV`）走的是另一套，**不涉及 `A005`**：
```jass
call UnitAddAbility(Vn[kV],'S021')                     // 虔诚（我方 f_override=S021 ✅）
set lV[0]=AddSpecialEffectTarget("Crown.mdl",Vn[kV],"head")   // 王冠
set hn[kV]=hn[kV]*9./10.                               // 受伤 ×0.9（我方 dmg_taken_mult ✅）
set To[kV]=To[kV]*9./10.                               // 熔岩 ×0.9（我方 lava_taken_mult ✅）
```
→ 我方国王实现与本段**逐项一致**，与 `A005` 无关。

#### 1. 098c 是**双轨 HP 系统**
- **玩法血量**：映射侧 `Fn[id]`（当前 HP）+ `gv[]`（`hR = gv/.03`）。
- **显示血量**：`SetUnitState(UNIT_STATE_LIFE, Fn[id])` 写回单位驱动血条。
- `BX(id, heal)` 里 **`Fn` 被 WC3 `MAX_LIFE` 夹住** → `A005`（改 `MAX_LIFE`）**会限制玩法血量上限**，不是纯视觉。

#### 2. `A005` 逐级表（`alev=24`；098b 人工转录与 098c **逐项一致**）
```
L3..L12  = +90 ×(L-2)   → +90 … +900
L15..L24 = -90 ×(L-14)  → -90 … -900
（L1 = 0；L2/L13/L14 无条目 = 0）
```

#### 3. 两处调用构成**正负相消的一对** → 作者意图是「当化身期间改变血量上限」
- 化身：`L = n+12` → **负段** `-90×(n-2)`
- 还原：`L = n`（`GV` = 设定化身时保存的 `qn`）→ **正段** `+90×(n-2)`，恰好抵消
- 两处都是 `add → SetUnitAbilityLevel → remove`，中间**没有**补血/夹血调用。

#### 4. 结论与实现决策
- **意图明确**：作者要让**化身在成为化身期间**按人数改变血量上限，并在卸任时还原（因此他认为 `remove` 后效果仍在）。
- **数值存疑**：按此读法，化身上限 = `100-90×(n-2)`：n≤2 → 100、**n=3 → 10**、n≥4 → 夹到 1。
  10 血/1 血的化身在 3 人以上局几乎不可玩，与「化身有 `Gn×1.5` 等增益」并列显得极端。
- **另一种可能是 `add→set→remove` 在 WC3 里是 no-op**（则两处都无效果，作者白写）。
- 两种读法各有不合理处，**静态数据无法判定**，需真机验证（开一局化身模式看血条上限是否随人数变化）。
- **我方暂不实装**（保持：化身不改变血量）。

#### 5. 同段落中**行为明确**但尚未实装的一项
`set Hn[FV] = Hn[FV] / (qn/1.5)` —— 化身的击退系数按人数削减（n 人 → ÷(n/1.5)）。
我方 `set_roles` 已实现同段的半径 50 / `Gn×1.5` / `jn×1.2`，**仅此条未做**。

## B 轮复核：③ 背包容量（**发现待查差异**）

**双方数据**：

| 背包研究购买数 | `L = 1 + 购买数` | w3q `R000` tooltip | 按其增量累进（基础 1） | 我方 `(L²+L)/2` |

**我方现状**：`meta.rs::inventory_slots()` = `0.5×(L²+L)`，注释称来源为 098c `bD` 实证；
`CAPS[3] = 3` → 玩家最多到 `L = 4` → 10 格。

**待查（下次）**：真正的格数来源应是**能力 `S128` 的逐级 item-capacity**（war3 里物品栏格数由能力决定，
`S128` 由 `IncUnitAbilityLevel` 提升，见 25563）。需从 `war3map.w3a` 读 `S128` 的逐级字段确认，
而不是继续用公式外推 —— 若 `S128` 只到 Lv3/4，则上限与"10 格"都要重新对。


### ③ 结论（已定性）：背包容量是**有意偏离**，不是 bug

判定：**保留我方实现**（`1/3/6/10`），前三项与 098c 完全一致 ✅，第四项为记录在案的扩展。

### ⑤ 续：`po`（伤害金）定性 + 一处**候选差异**

**`po` 不是"每点伤害给钱"**，而是**回合结算金**（默认 **1**）：

```
213    integer po=1                        ← 全局默认值
5378 / 5469 / 5670 / 5761  ... + po       ← 四处加法全在「回合结算/名次」处理里（4 种模式各一处）
19010  set po=S2I(dd)                     ← 房主可在设置里改（设置 id 16「Damage Gold Reward」）
```

**与我方对照**：我方 `MatchState::give_round_gold()` 每回合给 `config.gold_per_round`，
语义与 `po` **一致**（回合结算金、按设置可调）✅ —— 但**默认值不同**：

| | 我方 | 098c |
|---|---|---|
| 回合结算金 | `gold_per_round` 默认 **10** | `po` 默认 **1** |

**判定：候选差异，暂不改动**。理由：098c 的多数奖励（`lo`/`Lo`/`Mo` 等）默认值来自
**对话框默认项**而非全局初始化（`po` 是唯一能在全局声明处看到默认值的），
单凭 `po=1` 就改我方的 10 会引入新的不确定。**待办**：找出设置对话框里 12–16 号项的**默认值来源**
（`dd`/`Dd` 的初值），再一次性对齐全部 7 项默认值。

**⑤ 小结**：
- 结构对齐 ✅（击杀/助攻/回合/胜利四条线都在；`ED` 物品回收价一致 ✅）
- 缺"**点数 vs 金币**"的区分（098c 是 `ko/Ko/mo` 点数 + `lo/Lo/Mo/po` 金币两套）
