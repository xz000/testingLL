# 帧同步基座稳固计划（LOCKSTEP_FOUNDATION）

> 创建于 2026-08-15，紧接「⚠ 2026-08-15 修复」之后。
> 目标：把网络层从「能跑通」做到「稳定、可测、防假绿」，并把「延迟掩盖」与「手感」两条线在计划层面彻底分清。
> 配合 `PLAN.md`（总计划）、`NEXT_STEPS.md`（交接/下一步）、`SKILL_SPEC.md`（技能真值表）一起看。

---

## 0. 背景：为什么现在专门立这份计划

本轮排查揪出网络层一个能**静默吞掉全部输入、且测试全员假绿**的封帧 bug（见 NEXT_STEPS「⚠ 2026-08-15 修复」）。
它暴露的不是一个 bug，而是三个根因性问题，都值得用「一份明确计划」来收口：

1. **帧同步测试缺乏「防假绿」纪律**：旧测试只比较「两个 World 是否相等」，不证明「确实推进过/输入确实生效」→ 网络偷偷坏掉时测试照样绿。
2. **帧封装函数 `up_packet`/`frame_packet` 的 `out.clear()` 副作用**是「先 push tag 再被清」这类排列错法的温床 → 属于接口设计债。
3. **「手感/前后摇」被误当成「网络延迟掩盖」指标** → 会污染阶段 3 的验收标准，需要从目标层面厘清。

这份计划只聚焦「帧同步基座」，不展开美术/菜单/Steam 等后续阶段（那些仍在 PLAN.md 里）。

---

## 1. 计划的顶层判断（为什么"顺序没大错"，但要多做一件"地基先行"）

- **Rust 重制的方向基本是对的**：确定性地基（定点 + 确定性 RNG + 纯函数 step）最先做、用 `trait Transport` 做传输无关、ggez 只做渲染、帧同步自写 —— 这些都是对的。
- **"先做单机 demo"没做错**：帧同步的地基是「确定性」问题，不是「网络」问题，必须先有纯逻辑核心才能谈锁步。
- **但这轮暴露的真问题是**：**最小锁步骨架（确定性核心 + 最小 UDP 收发 + 防假绿测试）搭得太晚**，导致网络层的封帧 bug 到阶段 3 才暴露。以后应把「锁步骨架」当作从第一天就存在的第一类公民，而不是等玩法做全才补。

> 一句话：**不是否定单机 demo，而是建议「锁步骨架」与「玩法」并行长、一开始就在。** 现在已经补上了，本计划就是把这个补丁整理成正式基座。

---

## 2. 定点数选型结论（核实 + 决策，不换）

- 当前 `Fix64 = fixed::types::I32F32`（64 位，32 整数 + 32 小数，范围约 ±2^31，分辨率 2^-32）。
- 对当前游戏量级（场地半径 20、球速个位数）**绰绰有余，不会溢出/丢精度**。
- `fixed` crate 成熟、纯整数、跨平台确定 —— 满足锁步需要。
- **决策**：
  1. **不换**。`fixed`(1.28 锁版) + `cordic`(确定性整数三角) 对标原版 `FixMath`，方向一致。
  2. **升级要谨慎**：`fixed=1.28` 是固锁（rustc 1.88 装不了 1.31）。将来升 rustc 时可升 `fixed`，但**必须重跑全部锁步测试**，因为定点位一致性在版本间必须保持不变。
  3. **文档勘误（小）**：`fix.rs` 顶部注释把 `I32F32` 写成「Q32.32」，实际是「32 整数+32 小数」（范围由整数位决定）。把注释改准确，避免误解。

---

## 3. 引擎是否自带帧同步 → 结论：不带，自写是对的方向（不采纳"换 ggrs"）

- ggez 是纯渲染/输入库，无任何联网/同步机制。
- Unity 的默认联网是状态同步，不提供「定点 + 逐位回放」的纯 lockstep（原版 demo 也是自己写的 `FixMath` + 帧同步）。
- Rust 生态里没有匹配"定点逐位 lockstep"的开箱 crate；`ggrs`（GGPO）配浮点 + 依赖一堆，与当前目标（定点逐位）不贴合，**不采纳**。
- **决策**：维持 `game-core`(确定性) + `net`(传输无关 lockstep) + `ggez`(渲染) 的架构。将来若要 GGPO 级延迟掩盖，也是在 `net` 之上叠一个新 `SyncLayer`，不换引擎。

## 4. 待做工作（按优先级，标记 ✅/⏳ 状态）

### 4.1 固化「帧同步测试防假绿」纪律  【✅ 已完成 2026-08-15】
- 代码层（已做）：`session_lockstep_over_udp` / `host_participates_as_player_zero` / `full_online_match_identical_worlds` / `two_client_links_stay_synced` 均加了：`collected.len() >= N`、`stepped > 0`、`world != 初始World`。

- 验收：任何「静默丢数据」的协议回归都会当场炸红。✅

### 4.2 重构帧封装 —— 消除 `out.clear()` 副作用  【✅ 已做 2026-08-15】
做法：
- 采纳原方案 A：`net/src/frame.rs` 的 `up_packet` → 返回 `Vec<u8>` 的纯函数，`frame_packet` → 返回 `Vec<u8>` 的纯函数；去掉 `out: &mut Vec<u8>` 参数与 `out.clear()`（签名层面杜绝“先 push tag 再被 clear”）。
- `session.rs` 的 `send_input`/`broadcast_frame` 改为：先取纯函数返回的 body，再手动拼 `TAG_INPUT`/`TAG_FRAME` 前缀。
- tag 与 index 职责在注释里写清：上行包 = `[TAG_INPUT][index][payload]`，下行帧 = `[TAG_FRAME][count][(idx)(len)(bytes)...]`。
- 回归：`lockstep_over_udp_reaches_identical_worlds`、`frame_roundtrip`、`frame_packet_roundtrip` + 全部 session 测试全绿。
- 验收：`cargo test --workspace` 80 全绿；`cargo clippy --workspace -- -D warnings` 无警告。✅

### 4.3 引「数值平衡层 Balance」解耦手感  【⏳ 待做，属稳健性，不紧急】
- 现状：`ACCEL=20/DECEL=40`、`START_RADIUS` 等纯数值常量硬编码在 `game-core` 各处，且被 PLAN 标记"纯数值调优可后做"。问题是：**改手感数值＝改 game-core → 破坏两端同版本确定性**。
- 改法：把全部手感/玩法数值收敛进一个 `Balance`（/`Tuning`) 结构体，随帧同步**版本号**一起同步；调手感改数据不改逻辑。
- 验收：调一个数值后，若两端用同一 Balance 版本，锁步仍逐位一致。

### 4.4 厘清「延迟掩盖」与「手感」目标  【✅ 判定已定，待写入 NEXT_STEPS 决策区】
- 判定：**当前纯 lockstep 阶段，KPI 是「本地/内网多开不阻塞、逐位一致」，不背负"在显示上掩盖延迟"**。
- `ACCEL/DECEL` 移动加减速、`windup/recovery` 前后摇 → **只当单机手感**，不作为延迟掩藏手段。
- 真正的延迟掩盖（输入缓冲 / 本地预测 / 乐观回滚）→ **划为一个独立、完整的后续分支**，叠在 `net` 之上，不污染 `game-core` 确定性。
- 待做（文档化）：在 PLAN.md / NEXT_STEPS 的「待议决策」里明确写清这条边界，避免后续用错误指标验收阶段 3。

### 4.5 本地 lockstep 多开稳定性手测  【辅助已做 ✅；真机手测 ⏳ 需人工】
**自动化辅助（✅ 已做 2026-08-15）：**
- **无头冒烟测试**：`net::tests::lockstep_8_player_max_capacity_smoke` —— host + 7 名 client（共 8 人，达上限）用真 UDP 跑 40 帧，验证到上限都锁步同步；严格带防假绿断言（合帧收齐 N / 逐位一致 / stepped / 输入生效），且有界循环。**注意测试内各端必须用相同 seed，否则初始布局不同、比对必败。**
- **一键多开脚本** `multi-launch.ps1` —— `powershell -File multi-launch.ps1 -Players N -Port P`，自动 build 后开 1 个 `--host` + (N-1) 个 `--join` 窗口，供真机手测。
