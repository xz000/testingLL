# 面向 Steamworks 的对局掉线/重连设计 RECONNECT.md

> 创建 2026-08-15。决策前提：**将来必须走 Steamworks 联机，且必须有重连功能**。
> 本文论证为什么纯 lockstep 不能直接做重连、给出「Host 权威 + 状态快照(方案 A)」为推荐过渡、
> 「专用服务器权威(方案 B / Dota2 式)」为最终形态，并落到现有代码的改动与落地顺序。
> 关联：`ROADMAP.md`(三大功能) · `NET_REWRITE.md`(lockstep 重写) · `ATTRIBUTE_SYSTEM.md`

## 0. 核心前提：为什么纯 lockstep 无法直接做重连
纯 lockstep = 每个端各自跑 World，靠**输入逐位对齐**推进；没有"当前世界快照可下发"的概念（世界在每人脑内）。
- 掉线者错过若干帧后，它的 World 停在旧处，别人继续前进 → 无法"从当前继续"。
- 因此：**要重连，必须有「当前状态从哪来」的统一可靠源**。

## 1. 两个可选方案

### 方案 A：Host 权威 + 周期状态快照（过渡，推荐先做）
不推翻 lockstep，host 额外当"状态权威"，定期保存 World 快照供重连。
1. **快照（host 侧）**：每 N 帧（或每随局），Host 保存「World(Clone) + 各玩家 PlayerConfig + round/phase/seq」→ 一条状态快照。
2. **重连者**：
   - 向 host 发 `ReconnectReq`；
   - host 返回最新快照 + 它在当前 seq 流的接回点；
   - 重连者用快照重建 World，并从当前 seq 开始继续上行（不必补错过的帧，直接从"现在"接入）。
3. **同步窗口**：重连瞬间 host 广播 `Resync(seq)`，全员从该 seq 重确认一条基线，之后正常 lockstep。
- 优点：保住现有 lockstep + 4.6 多局 + 4.7 预测；换 SteamTransport 时网络逻辑不变。
- 缺点：host 是唯一状态源，host 断需处理（见 §3 挂点）。

### 方案 B：专用服务器权威 / 状态同步（最终，Dota2 式）
- 一个权威进程持完整 World，各端上报输入、从服务器收**状态**（非锁步输入帧）。
- 掉线者回来直接从服务器拉当前状态 → 天然重连（Dota2/Source 正是如此）。
- 代价：放弃纯 lockstep，改状态同步；确定性放宽；工程量最大。
- **结论**：作为以后"Steam 对局规模/手感需求上来时"的最终形态，不直接跳。

## 2. 为什么「方案 A 优先、方案 B 后续」
- lockstep + 多局 + 乐观预测已投入很多，方案 A 保住这套资产，只加"host 快照 + 重连握手"。
- Steam 重连本质要"掉线回来能接上的当前状态"，方案 A 的 host 快照恰好给，且 Transport 换成 Steam 时逻辑不变。
- 仅当 Steam 对局延迟掩盖需求更高、host 也易断时，再上方案 B。

## 3. 两个必须同时设计的挂点

### 挂点 1：host 掉线（权威端消失）
方案 A 下 host 是唯一权威，host 断 = 状态源没了。三选一：
- **快照同步给候补端**（推荐）：每帧把最新快照顺带同步给 1 个候补端；host 断 → 候补用快照接管，其余端重连到新 host。
- 主机迁移：快照 + 选新 host。
- MVP 退化为"全端回大厅"。
建议：MVP 用「快照 + 候补端」。

### 挂点 2：本端进程崩溃 / 重连身份
- 进程崩溃无法主动重连 → 靠"重新启动后，用稳定身份（SteamID 天然可作）重新 join + 拉快照"。
- 需要给玩家一个稳定的"对战内身份"；局域网先用"玩家槽/昵称"，Steam 用 SteamID。

## 4. 与现有代码的对应改动（方案 A）
- `game-core`：
  - `World` 需可确定性序列化（现有 Clone/PartialEq 可扩展 serialize）→ 供快照。
  - `MatchState` 也需能存快照（round/phase/金币/技能等级），供重连者接管。
- `net/`：
  - proto 加 `ReconnectReq` / `Snapshot` / `Resync` 包。
  - `HostLockstep`/`ClientLockstep` 加"接回基线"：Client 收到快照 + `Resync(seq)` 后用快照建 World、`set_start_seq(seq)`、继续正常收发。
- `client`：
  - 重连入口：掉线 → 提示 → 尝试重连 → 拉快照 → 继续。
  - 断连/退出菜单需能区分"离开(离场)"与"掉线(可重连)"。
- `net/SteamTransport`（将来）：实现 `Transport`，`Peer = Steam 用户`；大厅 join/leave 映射重连身份。

## 5. 掉线与重连的区分（MVP 语义）
- **离场 / abandon**：主动退出 / 多次无法连回 → host 判"死亡/离场"，从等齐集合移除，其余继续（不卡全队）。可作"重连窗口到期"。
- **掉线 / drop**：短时断 → 保留槽位一段时间，允许通过 `ReconnectReq` + 快照接回。
- **重连窗口**：掉线后有"重连窗口"（如 30s），窗口内可重连；过期则按离场处理。
- 对齐 Dota2/War3：不因单点掉线崩全队；或体面结束、或其余继续。

## 6. 落地顺序（建议）
1. **局域网先落"方案 A 机制"**（用 UDP 可测）：host 周期性快照 + `ReconnectReq`/`Snapshot`/`Resync` + 掉线判定 + 掉线重连接回。
   - 先做"离场不卡全队"（掉线判定/移除）→ 再做"重连接回"（快照/Resync）。
2. 机制验证 OK 后接 Steam：换 `SteamTransport` + Steam 大厅身份，重连逻辑零改动。
3. 需要时再评估方案 B（服务器权威）。

## 7. 验收
- 局域网：某端中途断→重连后能用最新快照接回，其余端不卡、逐位一致继续。
- host 断：(候补接管 / 回大厅) 不使全队永久卡死。
- 接入 Steam 后：用 SteamID 重连同一把，能拿到当前状态继续，逻辑与局域网一致。

## 8. 与现有计划的衔接
- 先于/并联 `ROADMAP.M2 局域网` 与 `M3 Steam` 的重连需求。
- 掉线判定(离场)是"局域网退出处理"的前置（解决"关窗全队卡死"）。
- 重连(方案A)是通往 Steam 重连的同一套逻辑，只是局域网先用 UDP。
