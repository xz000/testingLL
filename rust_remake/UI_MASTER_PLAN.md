# UI 总体规划（Master Plan）

> 由 `LOBBY_UI_PLAN.md` 扩展而来。起因是连续暴露的**同一类**问题：
> ① 子界面早退导致覆盖层漏画、心跳被掐断；
> ② 同一个键被多处处理（`O` 开→立刻关、`Q` 关编辑却退了房）；
> ③ 文本输入态下按字母快捷键会**把字母打进文本框**；
> ④ 提示文字摆放位置被其它元素压住（层次靠"摆放顺序"维持）。
>
> 这些都不是"某处写错"，而是**缺少统一模型**：输入路由、绘制管线、排版网格、键位归属。

## 一、输入路由（InputMode）—— 本次新提出，优先级最高

**问题**：现在按键处理散在各界面里，没有"谁在吃键"的概念 →
房间名输入框中按 `M`/`R`/`O` 会**既改设置又输入字符**。

**模型**：任何时刻只有一个 `InputMode`，键的处理按模式分派：

| 模式 | 吃哪些键 | 不吃的键 |
|---|---|---|
| `Shortcuts`（默认） | 字母/数字/方向/回车等全部快捷键 | — |
| `TextInput(field)` | **仅**可打印字符 + Backspace/Delete + ←→（光标） + Enter（确认）/ Esc（取消） | **所有字母快捷键**（关键！） |
| `Overlay(kind)`（设置编辑器/好友面板） | 该覆盖层自己的键位 | 底层的所有键 |

**规则**：
1. 进入 `TextInput` 必须是**明确动作**（Enter/点击该字段）；退出必须 Esc/Tab/回车。
2. **全局白名单**在任何模式下都有效：`Esc`（返回上一层）、`F1–F3`、以及明确的"打开覆盖层"键（如对局中 `Esc`）。
3. 文本输入态下的"快捷键提示"应从底部提示行**移除或灰显**，避免误导。
4. **可单测**：`route(mode, key) -> Action`，用测试覆盖"文本态不触发快捷键"这类回归
   （就像 `keys.rs` 的 `main_wires_shared_confirm_contract` 那样，把契约固化成测试）。

## 二、绘制管线（单一入口 + 覆盖层最后画）

- 一个 `LobbyScreen`/`Screen` 状态机，**子界面不再提前 `return`**；
- 绘制顺序固定：**背景 → 底层界面 → 覆盖层（设置编辑器/好友面板/提示条）→ 全局提示**；
- 覆盖层统一：半透明遮罩 + 居中面板 + 面板内自己的页签/行/提示。

→ 从结构上消灭"加了界面却画不出来/被压住"（本系列已出现 3 次）。

## 三、排版（网格与区域）

- **基线单位 8px**；正文 14–16px、标题 22–54px 分档（沿用现有 `ui::theme`）；
- 每个界面固定四带，避免元素互相压：
  1. **标题带**（顶部 10–18%）
  2. **内容带**（中部，网格/列表）
  3. **状态带**（内容下方：金币/徽章/警告）
  4. **提示带**（**屏幕最底部**：按键说明）—— 本轮"提示被字段压住"就是提示放到了标题带里
- 列表一律走 `ui::scroll_window`；行高统一 `ui::theme::ROW_H`；
- 组件复用：`ui::row` / `text_left` / `text_right` / `panel`。**禁止**在界面里手搓矩形+文字。

## 四、界面清单与优先级

| 界面 | 现状 | 目标 |
|---|---|---|
| 主菜单 | 3 卡片 + 方向键 | 用统一管线重排（低优先） |
| 大厅菜单 | 创建/加入/返回 | 同上 |
| **建房设置** | 8 个文本/数字字段 + 设置编辑器 | **拆成两块**：房间信息（文本）｜设置摘要（只读，`O` 进编辑器）；文本字段用 `TextInput` 模式 |
| **房间列表** | 只读列表 | 每行显示 **`自定义 N 项`徽章**（从大厅元数据读设置串） |
| **房间（就绪）** | 玩家卡 + 倒计时 | 加设置徽章（已有）+ 底部提示带 |
| 房间信息编辑 | 房间名/备注/锁房/模式 | 并入统一管线；**不得**掐断心跳（已修） |
| 设置编辑器 | 四组 + 档位/自定义输入 | 独立 Screen；`TextInput` 模式用于自定义数值 |
| 对局 HUD / 学习配置 / 记分板 / 结算 | 已较完整 | 只做"提示带/网格"对齐 |

## 五、迁移顺序（更新）

1. **`LobbyAction` + `lobby_rows()`**（纯逻辑 + 单测；不改行为）
2. **`InputMode` 路由**（本次新提，优先级提到第 2）—— 先解决"字母打进文本框"
3. **单一绘制管线 + 覆盖层最后画**
4. 建房界面按第四节的**拆分**重排 + 文本态接 `TextInput`
5. 列表/房间徽章 + 键位总表进 `keys.rs` + 冲突检测测试
6. 局域网/单机路径接入

> 每步独立可提交、随时可停；每步都必须让 `cargo test --workspace` 与两套 clippy 保持全绿。

## 六、建房界面重构（用户指定，2026-09-12）

**目标**：整屏重构 + **键鼠都支持**（当前仅键盘）。

**现状问题**：
- 8 个字段靠 `↑↓←→` 导航，**鼠标完全不可用**（不能点选字段）；
- 输入只有键盘，按钮（如"创建房间"）也只能靠回车；
- 与设置编辑器（`O`）风格不统一：编辑器的行是"列表式"，建房界面是"表单式"。

**设计**（对齐商店重构的成功做法）：
1. **命中注册表**：`create_hitboxes: Vec<(Rect, CreateAction)>`（照搬 `learn_hitboxes: HitRegistry<LearnAction>`），
   绘制时 `push`，输入时 `hits_at(mouse)` 派发 —— **绘制与命中同源**，不会再有"看得见点不到"。
2. **`CreateAction`**：`FocusField(usize)` / `SetMode(u8)` / `CycleRegen` / `OpenSettings` / `Create` / `Cancel`
   / `StepField(usize, i32)`（字段两侧的 `−` / `+` 小按钮）。
3. **鼠标能力**：点击字段聚焦、点击 `−/+` 步进、点击"创建房间"按钮、点击设置徽章进编辑器、
   滚动切换字段；悬停高亮（沿用 `ui::RowState`）。
4. **键盘保留**：现有键位不变（含方向键/回车/M/R/O/Q）。
5. **排版**：已在第 2 步接上 `layout::bands` ✅；本次改为**表单 + 行内步进按钮**的统一列表式，
   与设置编辑器视觉一致。

**迁移**：① 命中注册 + `FocusField`（本轮做）→ ② `−/+` 步进按钮 → ③ 按钮化（创建/取消/设置）
→ ④ 与设置编辑器统一为同一套行渲染。

## 九、房间设置统一模型（2026-09-12）

设置被劈成两拨：**「建房时才能设」**（房名/备注/人数/轮数，在 `H` 界面）与
**「房内能设」**（经济/玩法/地图/模式，在 `O` 编辑器）；而其中多数**两边都该能改** ✗。
后果：`E` 界面职责混乱、"改了不知道如何生效"、两套保存语义、客户端无从下手。

**统一设计**：一份设置模型 + 一个设置界面 + 两种运行模式。

- **设置模型**：`MatchConfig`（轮数/经济/玩法/地图/模式，经设置串同步）
  ＋ `RoomMeta`（房名/备注 = 大厅元数据；人数上限 = Steam 建房时固定，只读）。
- **一个界面**，分组 `[Z]房间 [X]经济 [C]玩法 [V]地图 [M]模式`；
  `[Z]房间` = 房名 / 备注 / 总轮数 / 人数（只读 + 说明）。
- **两种模式**：`Create`（建房前，`H` 进入，底部 `[创建房间]` 才落地）
  ／ `Edit`（建房后，`O` 进入，关闭时发布）。
- **非房主**打开 = 只读 + 顶部提示「只有房主可以修改设置」。

### 用户裁定（2026-09-12）

1. **`E` 退休**：不再单独设「编辑房间信息」界面，房名/备注并入 `[Z]房间`；房内只用 `O`。
2. **发布时机 = 关闭编辑器时**（不是每次改动即发）：编辑器内随意改 → `Esc`/回车关闭时
   一次性同步本端 `match_*` + 世界层 → 发布设置串 → 各端应用并清空准备。
   底部状态行显示 `关闭即生效 · 自定义 N 项`。
3. **人数上限只读展示**，不做"目标人数"概念；关门靠锁房。

### 步骤 1 的真实难点（已定位）
`settings_ui` 的 `value/set/nudge` 目前只作用于 `MatchConfig`，而**房名/备注属于大厅元数据**。
因此行模型需支持**两个数据源**：建议引入 `SettingTarget::{Cfg, Meta}` 由 `value/set` 分派
（改动集中、可单测），而不是把大厅元数据硬塞进 `MatchConfig`。

### 迁移步骤（每步可独立提交、保持全绿）
1. `settings_ui` 增 `[Z]房间` 分组 + 双数据源（`SettingTarget`）
2. 编辑器支持 `Create`/`Edit` 两种模式（`Create` 底部显示 `[创建房间]`）
3. `H`/`O` 都打开该界面；`E` 退休
4. 关闭时发布 + 底部状态行
5. 非房主只读模式
6. 清理遗留（`steam_create_*` 缓冲、旧 E 绘制、死代码键盘分支）


## 十一、待办：中文输入法（IME）（2026-09-12 记录）

**现象**（用户实测）：房间名/备注可以用**英文**输入，但**切到中文输入法后打不出中文**；
并且**启用 IME 时多处交互异常**（不只菜单界面，对局内也有）。

**现状**：代码里只有一处 IME 相关逻辑 —— `ime_commit_suppresses_ascii(frame, last_ime_commit_frame)`，
用于"同一物理键不被 ASCII 白名单重复插入"（C8）。它只覆盖**对局内**的部分路径，
**没有**统一的 IME 提交入口 → 编辑框（设置编辑器文本行、旧房间信息界面）收不到中文。

**为什么留待以后**：这属于**输入层**的独立问题（键盘/IME/焦点），与 UI 结构无关；
修它需要（a）接入 `WindowEvent::Ime`（`Ime::Commit(text)`）→ 把提交文本写入**当前聚焦的输入缓冲**；
（b）与 `InputMode` 的 `TextInput` 模型合并（IME 只在文本态启用）；（c）各端一致性（IME 是本地事件，不进快照）。

**建议做法**：等 `InputMode` 落地时一起做 —— 那时"哪个缓冲在接收文本"是明确已知的，
IME 提交只需往它写；否则现在做要再散落一次。

**临时立场**：游戏中房间名/备注建议用英文（用户也可自适应）。


## 十二、已定性的设计问题：**开局前就发钱**（2026-09-12，用户发现）

**现象**：房间/就绪阶段（对局还没开始）HUD 与房间面板就已显示金币；
因此在房内修改「初始金币」看起来"不生效"（钱其实早就发过了）。

**根因**：`MatchState::new` 里直接调用
`give_starting_gold()` + `give_round_gold()`（`game-core/src/meta.rs` 约 701-702 行），
而 `enter_first_round()` 的注释还写着"参与奖已在构造时发放" —— 即**发放时机就是构造时**，
不是开局时。098c 是**开局时才发**。

**正确做法（待实施）**：把这两次发放从 `MatchState::new` 移到 `enter_first_round()`，
并用 `opening_gold_granted: bool` 保证**幂等**（首局配置期有两条路径会走到 `enter_first_round`：
`tick_learning` 倒计时结束、以及单机的 `finish_first_round_config`）。

**为什么当时回滚（诚实记录）**：影响面比预估大 —— 直接导致 **8 个测试**失败
（`round_start_gives_participation_gold` / `starting_gold_granted_once_at_creation_*` /
`kill_gives_gold` / `finish_round_rewards_placement_and_gold` /
`learning_then_advance_gives_round_gold_again` / `d6_economy_defaults_match_098b` /
`upgrade_skill_spends_gold_and_fails_when_poor` /
`first_round_config_countdown_enters_round_one_without_extra_gold`），
且需要同时核对客户端"就绪→开始"的调用链；当时剩余精力不足以稳妥完成 + 验证，
故**按纪律回滚**，记录于此待专门处理。

**实施清单（下次）**：
1. `MatchState::new` 去掉两次发放；`enter_first_round` 发放（幂等字段）
2. 核对客户端：`enter_first_round` 在"房主开始 / 倒计时结束 / 单机手动开始"三条路径上都被调用
3. 更新上述 8 个测试（把断言改为"开局后"）
4. 顺带：房间面板在**未开局**时金币显示为 0（或显示"—"），避免误解
